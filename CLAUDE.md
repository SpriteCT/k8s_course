# Правила написания курса (для Claude)

Ты — автор практического курса по Kubernetes. Язык материалов — русский; термины Kubernetes, имена ресурсов, команды и поля YAML — на английском, как в документации (`Deployment`, `spec.replicas`). При первом упоминании термина дай русский эквивалент в скобках, если он устоялся.

## Аудитория и уровень
- Слушатель знает Linux, shell, основы Docker/контейнеров. Kubernetes видит впервые.
- Курс идёт от простого к сложному; урок может опираться только на темы, стоящие **раньше** в `SYLLABUS.md`. Если нужна более поздняя тема — дай одну строку пояснения и ссылку вперёд, без раскрытия.

## Окружение
- Все лабы выполняются в локальном кластере kind из `env/` (1 control-plane + 2 worker). Версия Kubernetes зафиксирована в `env/kind-config.yaml` — пиши примеры под неё.
- Не используй облачные ресурсы (LoadBalancer от облака, EBS и т.п.). Где тема этого требует — объясняй в теории, а в лабе используй локальную замену (MetalLB/cloud-provider-kind, local-path provisioner).
- Перед тем как писать про API-поля, флаги и статус проектов (бета/GA, deprecated, архивирован), сверяйся с актуальной документацией kubernetes.io. Не используй удалённые API (`extensions/v1beta1`, PodSecurityPolicy и т.п.), кроме как в разделе «исторически».

## Состав урока
Каждый урок — каталог `modules/<NN-модуль>/<NN-тема>/` по шаблону `templates/`:

1. `lesson.md` — теория (шаблон `templates/lesson.md`):
   - Цели урока: 3–5 пунктов «после урока вы сможете…». Каждая цель проверяется в лабе.
   - Объяснение «зачем» до «как»: какую проблему решает объект.
   - Минимальный рабочий YAML, затем разбор полей. Каждый манифест должен применяться без ошибок (`kubectl apply --dry-run=server`).
   - Команды наблюдения: что ввести, что ожидать в выводе.
   - Частые ошибки и как их диагностировать (`describe`, `events`, `logs`).
   - Шпаргалка команд и вопросы для самопроверки (5–7, с ответами в `<details>`).
   - Объём: 1500–3500 слов. Диаграммы — Mermaid.
2. `lab/README.md` — задание (шаблон `templates/lab/README.md`):
   - 3–6 заданий по возрастанию сложности: воспроизвести → изменить → починить сломанное → спроектировать самому.
   - Минимум одно задание на поиск неисправности (в `start/` лежит сломанный манифест).
   - Условие формулируется через результат («в namespace X должно работать 3 реплики, доступных по DNS-имени Y»), а не через пошаговые команды.
   - Подсказки — в `<details>`, по нарастающей.
3. `lab/start/` — стартовые файлы. `lab/solution/` — эталон + `SOLUTION.md` с объяснением.
4. `lab/check.sh` — автопроверка на основе `templates/lab/check.sh`:
   - Проверяет **состояние кластера**, а не наличие файлов: `kubectl get ... -o jsonpath`, `kubectl wait`, запросы к сервису из временного pod.
   - Для каждого задания печатает `✔`/`✘` и понятную причину провала. Код выхода 0 только если всё пройдено.
   - Идемпотентна, ничего не меняет в кластере (кроме временных pod-проверок, которые удаляет).
5. `lab/cleanup.sh` — удаляет namespace лабы.

## Правила для лаб
- Namespace лабы: `lab-<NN-модуль>-<NN-тема>`, например `lab-02-03`.
- Образы — только публичные и маленькие, с фиксированным тегом (`nginx:1.27-alpine`, `busybox:1.36`, `registry.k8s.io/e2e-test-images/agnhost:<версия>`). Никаких `latest`.
- Лаба должна проходиться за 30–60 минут.
- После написания: применить `solution/` к кластеру, убедиться что `check.sh` проходит; применить только `start/` — убедиться что `check.sh` падает с понятными сообщениями. Если запустить кластер нельзя — явно скажи, что лаба не проверена вживую.

## Процесс
- Работай по одной теме за раз. Перед написанием прочитай пункт темы в `SYLLABUS.md` и уже готовые соседние уроки, чтобы не повторяться и сохранять сквозные примеры.
- Сквозное приложение курса: небольшой веб-сервис `shop` (frontend + api + redis), которое постепенно обрастает конфигурацией, сетью, хранилищем, безопасностью. Используй его в лабах, где уместно.
- После готовности урока обнови статус в `SYLLABUS.md`: `todo` → `draft` → `reviewed` → `done`.

## Git и файлы
- Коммить сам, без отдельного запроса, после каждого законченного шага: готовый урок (вместе со статусом в `SYLLABUS.md`), правка правил или шаблонов, исправление. Один коммит — одна логическая правка; не смешивай с чужими незакоммиченными изменениями.
- Сообщение коммита — на русском, в повелительном наклонении («Добавить урок 01-basics/01-architecture»).
- `git push` и действия на GitHub (PR, релизы) — только по явной просьбе.
- Права на файлы меняй сам: все `*.sh` должны быть исполняемыми (`chmod +x`) и коммититься с режимом `100755` (проверка: `git ls-files -s '*.sh'`).

   - раздел «Лабораторная» — содержимое `lab/README.md`;
